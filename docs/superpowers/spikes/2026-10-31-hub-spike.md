Owner-run. Agents cannot read Claude credentials. Output goes to `spikes/cloud-sessions/out/` (git-ignored).

```text
dotnet run --project spikes/cloud-sessions -- q9 --answer-via tool-result
dotnet run --project spikes/cloud-sessions -- q9 --answer-via control-response
dotnet run --project spikes/cloud-sessions -- q9 --skills-probe
```

Expected: one of the first two makes the model reply with "Banana". Raw events land in `out/q9-events.jsonl` (pending item) and `out/q9-answered.jsonl` (after the answer). Copy the pending `AskUserQuestion` event into `runtime/tests/Fyrd.Core.Tests/Fixtures/ask-user-pending.json` and the post-answer events into `ask-user-answered.json` (JSON array of raw events).

## claude.ai prompt

Paste into a claude.ai/code session in the Default environment and record the answers.

```text
1. List your available skills and say whether any named fyrd-* appear.
2. Fetch https://claude.ai/artifact/LyjRt8594EXGq4V8UsQn5E with any tool you have and say which tool worked.
```

`q9 --skills-probe` sends the same prompt in an API session, to check whether account skills load in `/v1/sessions` sessions.

## Results

### Answer route and shape (owner runs, 2026-10-31; 3 runs)

**How a question appears.**
1. The worker emits an assistant `tool_use` named `AskUserQuestion`.
2. It then emits a `control_request` event with `request.subtype: "can_use_tool"`, `tool_name: "AskUserQuestion"`, `requires_user_interaction: true`, `input.questions[]` (`question`, `header`, `multiSelect`, `options[{label, description}]`) and a `request_id`.
3. While the question waits, `GET /v1/sessions/{id}` shows `session_status: requires_action`, `post_turn_summary.status_category: need_input` and `needs_action: "Approve or deny AskUserQuestion"`.

**What a real answer looks like.** In every run, a client other than the spike answered within about 10–40 s. Its `initialize` request named `sdkMcpServers: ["ccd_session"]`, which is the Claude desktop app.
- The answer is a `control_response`:
  ```json
  {"type":"control_response","response":{"subtype":"success","request_id":"<can_use_tool request_id>",
   "response":{"behavior":"allow","toolUseID":"<tool_use id>","tool_name":"AskUserQuestion",
     "updatedInput":{"questions":[...original...],"answers":{"<question text>":"<option label>"}}}}}
  ```
- The worker then writes a `tool_result` user event: `Your questions have been answered: "Pick a fruit"="Banana"...`.
- **A question is pending** while its `can_use_tool` `request_id` has no `control_response` with the same `request_id`.

**Spike's own answer: works (run 4, 14:02).** No other client was open this time.
- The question waited in `requires_action` for 60 s or more.
- The spike posted the client shape above to `POST /v1/code/sessions/cse_<id>/events` as `{"events":[{"payload":<control_response>}]}` with Fyrd's bearer token, and got HTTP 200.
- The session resumed, and the model replied "You picked **Banana**."
- So the console can answer questions. Answer only questions that are still pending: in runs 1–3, a late second answer after the desktop app had already answered confused the model.

**`tool-result` route: does not work (run 5).**
- With no other client open, a plain `tool_result` user event left the session in `requires_action`, still showing the question in the UI.
- Only the `control_response` answers a pending `can_use_tool` request.

**Fixtures:** `runtime/tests/Fyrd.Core.Tests/Fixtures/ask-user-pending.json` holds the events before the answer, and `ask-user-answered.json` holds all of them. Large `control_response` payloads are trimmed.

### Account skills

- In a claude.ai/code session, account and plugin skills **do** appear (anthropic-skills, engineering, slack-by-salesforce, and others). No `fyrd-*` skills exist yet, as expected, since none are uploaded.
- **API sessions (run 6, `q9 --skills-probe`, 14:10):** a session created through `/v1/sessions` listed the account's `anthropic-skills:*` skills (docs, pdf, skill-creator, and others) and the built-in ones.
  - Org and plugin skill groups shown in the web session (engineering, slack-by-salesforce, and others) were absent.
  - **So account skills load in Fyrd-created sessions, and the `fyrd-*` skills will reach the Controller once uploaded.** The fallback (pasting skill bodies into the Controller prompt) is not needed.
  - The same session also read the artifact link with the Artifact tool.

### Connectors (smoke run, 2026-10-31)

**Symptom:** the Controller, created by Fyrd, had no `claude-code-remote` tools, so it couldn't create sessions.

**Findings:**
- **Fyrd-created sessions get no claude.ai connectors.** A no-repo session made through the API (`/v1/sessions` or `/v1/code/sessions`) starts with `init mcp_servers: []`.
- **A repo source is not the reason.** With a repo source, the spike sessions did get `claude-code-remote` and `github`. A no-repo session created by hand on claude.ai had all of them.
- **What the hand-made session had** (`q10`):
  - `config.mcp_connector_ids` lists 16 connector ids.
  - Every claude.ai connector, `claude-code-remote` included, loaded as a `dynamic` MCP server.
  - The config also has `origin` and `permission_mode`.
- **Fyrd's token can't set connectors.** Creating through `/v1/code/sessions` with those 16 `mcp_connector_ids` returns HTTP 200, but the stored config comes back `mcp_connector_ids: []` and the session again has no MCP servers. The server drops connector ids from Fyrd's OAuth client.

**Owner's decision:** the owner creates the Controller by hand on claude.ai, and Fyrd **adopts** it:
- Fyrd stores its id.
- Fyrd sends the Controller prompt as the first message.

Peasants are created by the Controller's `create_session`, which is expected to inherit its connectors. Plan 2's peers could `send_message`. To be confirmed in the smoke run.

**2026-11-17 CLI create probe (PR #52):** the CLI can't create a cloud session non-interactively, so the connector question couldn't be tested this way.
- **Command:** `claude -p --cloud -n "Fyrd connector probe" --output-format json`, run from an empty temp directory with the prompt on stdin. CLI version 2.1.326.
- **Result:** exit 1, and no session was created. The CLI's stderr:
  > Error: --cloud cannot be combined with --print.
  > Starting a new cloud session with --cloud is interactive only: drop --print, or drop --cloud to run locally. To message an existing cloud session instead, pass its ID: `claude -p "message" --cloud <session-id>` (find IDs at claude.ai/code).
- **What this means:** `-p --cloud <id>` still sends to an existing session, which is what `ClaudeCliOwnerMessages.SendAsync` uses. A non-interactive create through `-p --cloud` is refused.

**2026-11-17 interactive create probe (PR #52), `claude --cloud "controller"`:** run from an empty temp directory, CLI 2.1.326, inside a Claude Code cloud container.
- **Without a terminal** (stdin, stdout and stderr all pipes): exit 1 at once, and no session was created. Stderr:
  > Error: --cloud "controller" is not a cloud session ID or URL.
  > Without an interactive terminal, --cloud can only send the prompt to an existing cloud session: pass its ID (session_... or cse_...) or its claude.ai/code URL. To start a new cloud session, run in an interactive terminal.
- **Under a pseudo-terminal** (`script -qfec`), the CLI shows its normal interactive screens before it creates anything:
  1. On a config that hasn't been onboarded, it stops at the first-run theme picker.
  2. With onboarding marked done, it stops at the "Quick safety check: Is this a project you created or one you trust?" folder-trust prompt for the temp directory. Both prompts wait for keyboard input.
- **With both pre-accepted** in a scratch `CLAUDE_CONFIG_DIR`: exit 1, `Error: Cloud session create failed: Request failed with status code 403`.
  - The container's CLI is signed in with the session's own `oauth_token`, which can't create cloud sessions.
  - No session was created, so the connector question is still open.
- **What this means for Fyrd:** a CLI create needs a real terminal.
  - On Windows that means hosting the CLI in a ConPTY.
  - It also means handling or pre-accepting the onboarding and folder-trust prompts, then scraping the session id from the terminal UI.
- **To run this probe on the owner's machine:** `pwsh ./scripts/probe-cloud-create.ps1`. It runs `claude --cloud "controller"` from a fresh temp directory, records or asks for the CLI's output, sends one probe prompt to the new session, and writes a report on where the session id appears and whether `claude-code-remote` is present.

**2026-11-17 owner's create probe (PR #52), `claude --cloud "controller"` on Windows, CLI 2.1.326:** run with `scripts/probe-cloud-create.ps1` from a fresh temp directory with the owner's own login. The CLI created the session, printed this and exited:

```
Created cloud session: Controller
View: https://claude.ai/code/session_01SQSYWZZdNyXRzob9SmbNhQ?from=cli&m=0
Resume with: claude --teleport session_01SQSYWZZdNyXRzob9SmbNhQ
This folder is not a git repository, so the cloud session starts empty: nothing from this folder is copied into it.
```

- **Connectors: present.** The session's `init` event lists `claude-code-remote` as connected, with `mcp__claude-code-remote__create_session` and the rest of its tools, plus the account's plugins. So a CLI-created session can start peasants, unlike the `/v1/sessions` sessions above.
- **Title and first turn:** the description became the title ("Controller") and the session's first user turn: the session answered "controller" by asking which controller to write. Fyrd therefore sends the whole Controller prompt as a second turn with `claude -p --cloud <id>`, and the prompt's first line says the "controller" message only named the session.
- **What Fyrd does with this:** `ClaudeCliOwnerMessages.CreateAsync` runs `claude --cloud controller` in a pseudo terminal (ConPTY on Windows, `script` elsewhere) from `<FYRD_HOME>/hub/controller-launch`, reads the id from the `View:` or `Resume with:` line, and stops the CLI if it lingers. If the CLI shows its folder-trust or first-run prompt instead, Fyrd stops it and tells the owner to answer that prompt once in a terminal of their own.
