# Controller skills

Six request skills the Fyrd Controller cloud session uses: `fyrd:research`, `fyrd:build`, `fyrd:investigate`, `fyrd:peasant`, `fyrd:tune`, `fyrd:watch`. Each is a skill of the fyrd plugin at `skills/<name>/SKILL.md` with `kind: controller-skill` in its front matter. The plugin is installed environment-wide, so every cloud session lists them, and none is reserved to the Controller (owner's decision): each description says when to use the skill and what it needs, the `<hub-settings>` and `<peasant-persona>` blocks of the Controller message and the claude-code-remote session tools, and each body opens with a **Needs:** line that says to start and change nothing without them. The rules live in the Controller persona, `skills/controller/SKILL.md`; each skill gives the tool-call steps for one request type, and the Controller runs one as `/fyrd:<name>`.

## Personas are plugin skills too

Every persona is a skill of the fyrd plugin at `skills/<id>/SKILL.md` with `kind: persona`: `fyrd:builder`, `fyrd:controller`, `fyrd:investigator`, `fyrd:monitor`, `fyrd:researcher`, `fyrd:reviewer`, `fyrd:tuner` and `fyrd:validator`. The skill body is the persona text and the only copy of it: the Fyrd service reads its personas from these files when it starts (`persona-name`, `persona-model` and `persona-locked` in the front matter give the rest), so a persona's name and text always come from the repo. The console's **Settings › Personas** is a table where you change only each persona's model; Fyrd keeps that choice in its own data, and **Reset** (or picking the default model again) goes back to `persona-model`. A model change never stops a persona from following its text in the repo. `skills/persona-seed-history.json` lists the hash of every version (`node scripts/seed-history.mjs` updates it); Fyrd uses it only to read the model of a persona that an older install stored whole: an unedited one takes today's default, an edited one keeps its model, and its stored name and text are ignored, as are custom personas an older console added. Fyrd keeps no copy of that old text: the first model change you make for such a persona overwrites its file with the new model, and **Reset** deletes the file, so a prompt you edited in an older console is gone without a warning (owner's decision). To keep it, copy it out of `~/.fyrd/data/hub/personas/<id>.json` before you change that persona's model. They set `disable-model-invocation: true`, so no session loads one by itself; you run `/fyrd:builder` in a session to make it act as a Builder, or to read a persona. Sessions the Controller starts still get their persona in their system prompt, from the `<peasant-persona>` blocks below. A session that runs a Validator, Reviewer or Investigator subagent gets no text of that persona: its persona tells it to brief the subagent to load the persona skill (`fyrd:validator`, `fyrd:reviewer`, `fyrd:investigator`) itself and follow only the sections the brief names, and to ask the owner, or go on without that check, when the subagent reports it couldn't load it. The persona skills still set `disable-model-invocation: true`, and the Skill tool refuses such a skill (only a person's `/fyrd:<id>` runs it), so for now such a subagent can't load its persona skill and reports that.

## Delivery (automatic)

Nothing is uploaded to claude.ai. The Fyrd service reads the request skills from `skills/*/SKILL.md` on every poll pass, so a `git pull` is enough, and puts them in the Controller's message after the peasant personas:

- **Plugin confirmed.** When the owner confirmed that the environment's setup script installs the fyrd plugin (Settings › Session skills, see `docs/session-skills.md`), the message carries one `<controller-skills>` block with a line per skill: the name the Controller loads it by (`fyrd:<name>`) and its description. The Controller loads the skill with the Skill tool before it acts. If the `fyrd:` skills are not in its list, the Controller session started before the plugin was installed: it doesn't act on the request and tells the owner to replace the Controller (Sessions › **Replace Controller**, then **Create Controller**, see [After edits](#after-edits)). The Controller runs the skill bodies of the plugin version Claude Code cached when its session started: a change to a body reaches it only after the plugin's version is bumped, `/plugin marketplace update fyrd` runs, and a new Controller session starts. A `git pull` alone changes only the names and descriptions in its message.
- **Otherwise** the message embeds each skill as a `<controller-skill name="fyrd:<name>">` block with its whole text, so a Controller works without the plugin. A block wins over a plugin skill of the same name.

The same message carries one `<peasant-persona>` block per role with the whole persona and, after it, the role's session skills (`runtime/src/Fyrd.Core/Hub/SessionSkills.cs`, `docs/session-skills.md`): a `# Session skills` section with one line per plugin skill (`fyrd:<name>`) when the owner confirmed that the environment's setup script installs the fyrd plugin, else, and for a skill edited or added in the console, the skill's whole body as a section. The Controller copies the block's text as it is into the `append_system_prompt` of a session of that role, so it needs no rule of its own for session skills. The message carries no subagent text: it once held `<subagent-persona-text>` blocks that the Controller copied into the `append_system_prompt` of a Builder, Researcher, Validator or Monitor, and the owner replaced them with subagents that load their persona skill themselves.

The first time a service that has this feature polls an existing Controller, it sends the instructions once (there is no stored hash yet); that is how existing Controllers receive the inline skills. After that, when a skill, a persona, or the Controller settings change, the service re-sends the instructions to the live Controller as soon as it is idle. A persona model changed in Settings reaches the Controller the same way (the `model` of its `<peasant-persona>` block changes). Persona text is read when the service starts, so after a `git pull` that changes a persona, restart Fyrd (`/fyrd:down`, then `/fyrd:up`). The message says the latest instructions replace earlier ones.

## One-time cleanup

If you uploaded the `fyrd-*` skills to claude.ai earlier, remove the uploaded fyrd-* skills: open Settings > Capabilities > Skills and delete (or disable) `fyrd-research`, `fyrd-build`, `fyrd-peasant` and `fyrd-watch`. Until you do, a stale copy stays visible to every session. The plugin skills that replace them are named `fyrd:<name>`.

## Create the Controller

In the Fyrd console open Sessions and choose **Create Controller**. Fyrd runs your signed-in `claude` CLI as `claude --cloud controller` to start a new cloud session at https://claude.ai/code, reads the new session's id from what the CLI prints, then sends the whole opening prompt (instructions, skills, settings and memory) to it with `claude -p --cloud <id>`, so the session is your own and reads the prompt as yours. The CLI only creates a session from an interactive terminal, so Fyrd runs it in a hidden pseudo terminal (ConPTY on Windows). To check that part on your Windows machine without creating a session, run `pwsh ./scripts/test-conpty.ps1`. It runs from `<FYRD_HOME>/hub/controller-launch`, which isn't a git repository, so the session needs no repo and starts empty. It runs in your CLI's default cloud environment: the hub's `environment_id` setting is not passed to the CLI (`--environment` only takes self-hosted `ccpool_` environments).

- **The session's first message is just "controller":** that is the description the CLI starts it with. The opening prompt that follows says so.
- **First-run prompts:** if the CLI asks whether to trust `controller-launch`, or asks first-run setup questions, Fyrd stops it and says so. Open a terminal in that folder, run `claude`, answer the prompt once, type `/exit`, and create the Controller again.
- **If the prompt isn't delivered:** the session was still created and Fyrd keeps it. Choose **Create Controller** again: Fyrd resends the prompt to that same session instead of creating another one.

## After edits

Skill edits and persona model changes reach a live Controller by themselves, except a request skill body change once the plugin is confirmed (see [Delivery](#delivery-automatic)). Replace the Controller after you confirm the plugin in Settings › Session skills, too: a Controller that started before the plugin was installed has no `fyrd:` skills in its list. Otherwise, choose **Replace Controller** next to Open Controller only if you want a fresh conversation. Replace Controller archives the current Controller. Then choose **Create Controller** as above.
